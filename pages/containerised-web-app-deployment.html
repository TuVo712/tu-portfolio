01 / The challenge

Building a web application is only part of delivering it. The team also needed a repeatable way to package frontend and backend services, configure networking, test changes before release and verify that deployed services were healthy.

Engineering question: How can we move a multi-service application from source code to a running environment while reducing deployment risk?

02 / How the system fits together

The application combined a built frontend served by Nginx with a Django API. Docker images provided consistent runtime environments, while Docker Swarm stack definitions described the deployed services on AWS EC2.

Docker images → Docker Swarm services → AWS EC2

The frontend's multi-stage Dockerfile builds the Node application, then copies the compiled output into a smaller Nginx runtime image. Nginx handles client-side routes and forwards /api/ requests to the backend service.

03 / What I worked on

✳ Frontend containerisation

Worked with the production frontend image, using a Node build stage and Nginx to serve the compiled application.

↗ Routing and health checks

Worked with frontend routing and API proxy configuration; checked deployed endpoints during troubleshooting.

↩ Green deployment and recovery

Authored the green Docker Swarm stack configuration and worked through rollback testing.

The green stack used separate published ports (8080 for the frontend and 8001 for the API), allowing it to be deployed alongside the original stack where infrastructure permitted.

Teamwork note: The Jenkins pipeline was a team deliverable. I describe its overall flow below without claiming sole authorship.

04 / From commit to deployment

The team's Jenkinsfile defined a staged workflow for building and checking the application before production deployment.

01Checkout & build images
02Backend tests & Trivy scan
03Publish versioned images
04Deploy to staging
05Smoke & Playwright tests
06Deploy & verify production

The staging checks covered frontend availability, API health and readiness, and a version endpoint. Production deployment checked expected replica counts and API readiness.

Technical detail: In the shared Jenkinsfile, Trivy used --exit-code 0, so vulnerability findings were reported rather than used as a blocking release gate.

05 / Deployment and recovery

To explore a safer release strategy, I prepared a separate green stack with its own published ports and readiness checks. This was a foundation for blue-green deployment, where a candidate release can be evaluated separately before traffic is switched.

Existing stackBlue / current

Frontend on port 80
API on port 8000

Candidate stackGreen

Frontend on port 8080
API on port 8001

During our earlier rollback testing, we checked a healthy endpoint, deliberately tested an unavailable endpoint, invoked a Docker Swarm service rollback and checked recovery. The complete original rollback script and final traffic-switching configuration have not yet been recovered, so I distinguish that testing from a verified, fully automated production rollback pipeline.

06 / What I learned

This project helped me connect application development with the operational decisions required to run software: container boundaries, proxy configuration, service health, staged validation and recovery planning.

It also showed me why deployment success needs more than a running container. A stronger production workflow would make security scans enforceable, verify application behaviour after switching traffic, and document rollback procedures and database migration compatibility.
