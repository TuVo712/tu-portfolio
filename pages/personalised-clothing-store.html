01 / The challenge

Most online clothing stores let shoppers choose from predefined products. Our proposed platform explored a more personal experience: allowing customers to customise clothing with their own text, images and patches before purchasing.

Design question: How could we turn a flexible clothing-customisation idea into a system with clear requirements, understandable user journeys and a maintainable architecture?

Rather than building a live e-commerce service, this academic project focused on analysis, modelling and design.

02 / Understanding the requirements

We identified the main customer journeys and refined the proposed scope into a more manageable set of features. The concept covered browsing clothing categories, searching for products, personalising designs and progressing towards a purchase.

✿Explore products

Browse clothing categories and search for specific items as distinct actions.

✎Make it yours

Personalise garments with text, images or patches and save design ideas.

♡Preview & decide

Explore a proposed camera-based fit preview, shopping cart and account flow.

Features such as virtual fitting were proposed capabilities, not working computer-vision functionality. Separating requirements from implementation helped keep our documentation honest and testable.

03 / Designing the system

We used UML models to describe how users, application components and data would interact. The design work included sequence, class and activity diagrams, alongside discussion of the MVC architectural pattern and Factory Method and Singleton design patterns.

04 / My role in the team

My main responsibility was keeping the team’s work coordinated and coherent, while also contributing directly to the system-design artefacts.

✳ Coordinating the work

Assigned responsibilities and deadlines, followed up on progress and managed communication with the lecturer.

✎ Refining the models

Redrew two sequence diagrams and helped draft the class and activity diagrams.

♡ Bringing the pieces together

Structured the assessment documentation, refined Figma mockups and reviewed teammates’ work for consistency.

This was a collaborative assignment: the full requirements set and design package were team outputs, not work I completed alone.

05 / Planning how to validate it

We connected requirements to test planning so that proposed features could be evaluated against expected behaviour. The documentation included testing considerations and traceability between the system’s requirements and its design.

EXAMPLE REQUIREMENTBrowsing

As a guest user, I want to browse clothing categories so that I can explore available items.

Example acceptance checkA guest can select a category and view its available products without signing in.

Project scope: These are design and test-planning artefacts. The project should not be mistaken for a deployed online store or evidence that every proposed feature was implemented and tested.

If shareable UML diagrams or interface mockups become available, this is where they can be added to make the design process more tangible.

06 / What I learned

This project showed me that software engineering begins well before the first line of production code. Good requirements and diagrams help a team uncover ambiguity, discuss trade-offs and build a shared understanding of what the system should do.

It also strengthened my experience coordinating people and reviewing work across different deliverables. If the concept were developed further, I would prioritise validating the customisation journey with users, then building and testing a small end-to-end slice before expanding to features such as virtual fitting.
